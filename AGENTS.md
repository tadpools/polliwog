# agents.md - the operating procedure

local only, never pushed. tadpole's convention, inherited. this file
says how an agent works on polliwog: pacing, verification, and the
honesty law. philosophy.md says why; style.md says how it reads;
github.md says how it ships. a conflict resolves upward: this file
yields to philosophy.md.

## the honesty law (absolute, non-negotiable)

absolutely no hardcoded or fake values. everything must be genuinely
tested. absolutely no lies. this is the highest-priority rule in this
file and it yields to nothing except the premise. spelled out:

### no hardcoded values

- no benchmark numbers, throughput figures, ratio percentages, or
  timing claims anywhere - docs, readme, issues, pull requests,
  commit messages - unless copied from a real run you personally
  executed, with the command and date cited beside the number.
- no magic constants presented as measured. every constant in the
  code carries a provenance comment (spec section, upstream doc, or a
  fixture that pins it). a constant whose provenance cannot be named
  gets deleted, not excused.
- no placeholder values that ship as if real. `0`, `TODO`, `X`,
  example bytes in production paths are bugs, not style.

### no fake fixtures or fabricated data

- fixtures presented as "captured" must be captured - from real runs
  of real backends, checked in with the command that produced them.
- synthetic fixtures are allowed and encouraged; they must be labeled
  synthetic and generated by a deterministic generator that is checked
  in. a fixture whose origin story is not checkable is a lie with
  bytes attached, and gets deleted.
- never paste test output you did not watch run. never screenshot a
  passing suite that did not pass on your machine. never claim ci
  results you did not wait for and read.

### genuine testing only

- a test that cannot fail is not a test; delete it.
- every claim in every doc must be checkable against this version's
  source. a doc claim that outruns the code is a bug with a deadline.
- before you say "it works", you have run it, watched it pass, and can
  name the command. before you say "it does not work", same standard.
- "it should work", "this usually passes", "i think the backend does
  x": none of these sentences may leave your mouth. go run it. if you
  cannot run it, say "unverified" out loud, in writing, next to the
  claim.
- versions pinned in dev/versions.md must match what the build
  actually compiled; the static_asserts exist to catch a mismatch, and
  reporting around them is a firing-grade violation of this file.

### no lies, anywhere

- the readme's "what does not exist yet" table must match reality on
  the day it is read, not the day it was written.
- stability tiers are claims with evidence. nothing is Stable without
  tests; nothing is described in public before it has a test.
- errors are never swallowed to make a run look green. a red build
  reported honestly beats a green build achieved by silence. if you
  catch yourself editing a test to make it pass instead of fixing the
  code, stop; that is the exact lie this file exists to prevent.
- "it was convenient" is not a reason. it was never a reason.

### research provenance (the freshness law)

- any claim of currency - "current release", "as of <date>", a
  version number, a changelog fact - must trace to a row in
  dev/research-log.md or carry an in-line citation with the fetch
  date and source url.
- research is done live (fetch the release page, read the changelog)
  before writing a freshness claim. training knowledge is not
  research; where it is used, the doc says so and flags the row for
  verification. unverified is a permitted state; unlabeled is not.
- the research log is append-only. corrections are new rows that name
  what they replace, never silent edits.
- before any milestone sitting: re-verify the pins in dev/versions.md
  against upstream release pages, add rows for anything that moved.
  a backend bump discovered late is a milestone risk; discovered at
  the sitting, it is a changelog line.
- benchmark-adjacent numbers (speeds, ratios, percentages) quoted
  from upstream release notes must name their source as
  upstream-reported; they are never rewritten as polliwog
  measurements. our own numbers come only from our own bench runs,
  with the command cited.

## session ritual

1. read dev/manifest.json, philosophy.md, architecture.md. skim
   style.md for the rule you are about to touch. check roadmap.md for
   where the work sits.
2. verify before writing: run the relevant tests first. know what
   passes before you change anything.
3. work in one sitting-sized step: one feature walks one step of the
   adoption ladder. small, complete, tested.
4. decisions: every non-obvious call earns two or three sentences in
   dev/decisions.md the day it is made - what was chosen, what it
   cost, what would change the answer.
5. gates before done: tests genuinely run and watched, warning-free
   on our code, clang-format applied, changelog entry, module map
   updated if a header changed.
6. close the sitting with the truth: what works, what does not, what
   is unverified. written down. no rounding up.

## what an agent does not do

- does not hardcode, fabricate, approximate, or round-truth.
- does not add a dependency without a written reason and a vendor
  replacement plan (philosophy.md, belief 5).
- does not invent api behavior the spec does not state.
- does not skip the failing test to save time.
- does not declare a milestone done without its gate, verified by
  running the gate commands, in the open, with output.

the library's whole product is trust: round-trip truth, byte truth,
error truth. an agent that lies about a benchmark is producing the one
bug the project cannot ship. when in doubt: run it, cite it, or cut
the claim.
